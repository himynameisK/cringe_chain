# Как это ломалось на самом деле

Ниже два сбоя, случившиеся на живой машине. Оба тихие: ни один инструмент
не сказал, что что-то не так.

## 1. Каталог журнала, которого не было

`apply` записал конфиг с `log.output`, указывающим в несуществующий каталог,
и перезапустил службу. `sing-box` не смог открыть файл журнала и завершился
с `FATAL`, не заняв порты.

Проверено на настоящем бинаре:

```
$ sing-box check -c cfg.json
(молча принимает)

$ sing-box run -c cfg.json
FATAL start service: start logger: open .../sing-box.log: no such file or directory
```

**`check` принимает такой конфиг.** Он проверяет форму, а не то, что произойдёт
при запуске. Это главный урок: валидный конфиг и работающая служба — разные
утверждения, и второе проверяется только попыткой.

Почему это стало катастрофой, а не мелочью: `HTTPS_PROXY` отправляет в прокси
**весь** трафик консольных программ. У PAC есть запасное «остальное напрямую»,
у переменной окружения — нет. Мёртвый порт означает отсутствие сети вообще.

Что теперь: `ensure_dirs` создаёт каталог журнала наравне с остальными, а
`apply` после перезапуска убеждается, что порты заняты, и сам возвращает
прежний конфиг, если нет.

## 2. Запись в файл, который никто не читает

Первый `apply` записал конфиг по пути из настроек — а служба Homebrew читает
путь, прошитый в её plist. Файл лёг на диск, служба перезапустилась со старым
конфигом, всё выглядело успешным. Изменения просто не применились.

Что теперь: `preflight` сравнивает путь из настроек с тем, который видит у
запущенного процесса (`ps`, флаг `--config`), и отказывается работать при
несовпадении.

## 3. Откат, который не откатывал

`off` снимает системные настройки, переменные окружения и останавливает службу.
Файл конфига он не трогает — значит, при сломанном конфиге любой последующий
запуск падал снова. Человек делал откат, видел, что не помогло, и терял время
на поиск причины не там.

Что теперь: конфиг версионируется (`*.backup-<время>`, хранятся последние 10),
есть команда `rollback`, а `off` прямо пишет, что файл остался нетронутым.

## Правило, которое стоит за всеми тремя

Проверять надо то состояние, о котором вопрос, а не соседнее.

- «конфиг валиден» ≠ «служба работает» — проверяется портом;
- «файл записан» ≠ «его читают» — проверяется путём у живого процесса;
- «настройки откатили» ≠ «причина устранена» — проверяется повторным запуском.


## Почему проверки заменены репетицией

Первая попытка чинить это была цепочкой условий: записали — проверили —
откатились, если плохо. Так появляется новая ветка на каждый новый способ
сломаться, и однажды случай не угадывается.

Репетиция устроена иначе. Берём ровно тот конфиг, который собираемся применить,
поднимаем на нём настоящий `sing-box` на свободных портах и ждём, пока он их
займёт. Любая причина отказа — забытый каталог, неверный ключ, занятый порт,
опечатка в параметре, ещё не встреченная нам причина — проявляется одинаково:
порт не занят. Одно условие вместо списка.

Проверено на настоящем бинаре:

```
конфиг с журналом в несуществующем каталоге
   sing-box check   -> принимает
   репетиция        -> отказ: FATAL start logger: no such file or directory

конфиг с неверной длиной ключа shadowsocks
   репетиция        -> отказ: bad key length, required 16, got 18
```

Второй случай нашёлся сам: репетиция отказала на фикстуре интеграционного
теста, где пароль был не той длины. Юнит-тест с заглушкой этого не заметил бы
никогда.

## Что остаётся непокрытым

Перезапуск самой службы — операция не мгновенная, и доли секунды между
остановкой старого процесса и готовностью нового порт свободен. Убрать это
совсем можно было бы только постоянным посредником, который держит порт
вечно, — лишняя деталь, которая сама становится точкой отказа.

Поэтому гарантия формулируется честно: катастрофический отказ (служба не
вернулась) исключён репетицией и откатом, а кратковременный разрыв при
перезапуске остаётся и лечится повтором запроса.
